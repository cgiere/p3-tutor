The context window 6 min

Big picture: the model has no memory of its own between calls. It only sees what the program puts in front of it on that call. That text is the context.

  • Token: the small chunk of text (a word or part of one) the model reads and writes. Providers bill by tokens, so tokens are your cost unit.
  • Context window: all the text the model can reference when generating a response, including the response itself. Anthropic calls it the model's "working memory", as opposed to what it learned in training (Claude docs: context windows).
  • It has a size limit. Current Claude models list up to 1M tokens; older ones 200k (same page). That is a ceiling, not a target.

A common mix-up

"A bigger window means the model uses everything in it well." Tempting because "can hold a textbook" sounds like "has read the textbook". But as the token count grows, accuracy and recall degrade, a phenomenon Anthropic calls context rot (docs). The model has a limited "attention budget", and each new token draws it down (Anthropic engineering). Goal: the smallest set of high-signal tokens that gets the job done. That is also the cheapest set.

What is kept between steps 6 min

Big picture: within one run, "memory" is just the program resending everything. Each step is a separate model call; the program appends each new request and result to the list of messages and sends the whole list again. Previous turns are preserved completely (docs).

Cost consequence: input cost across a run is the sum of every call's whole input, not the size of the final context. A large result early in a run is re-billed on every later step. Prompt caching changes what you pay for repeated prefixes, not whether they count toward the window (docs).

When the window fills up

Long runs can near the limit. Three standard levers (Anthropic engineering):

  • Compaction: summarize the conversation near the limit and start a fresh window with the summary. Keeps decisions and open problems, drops redundant tool output.
  • Tool-result clearing: delete old tool results you no longer need. Described there as one of the lightest forms of compaction.
  • Notes written outside the window (next section).

The trade-off: a summary is lossy. Whatever the summary leaves out is gone from the model's view.

A common mix-up

"The model remembers the conversation." It does not; your program resends it. Chat apps hide this, which is why it feels like memory. Consequence: if the program does not resend something, the model has never seen it.

Between sessions: notes as memory 6 min

Big picture: a new session starts with an empty window. Anything the assistant should "remember" next week must be written to storage by the program (a file or database) and loaded back in. This is structured note-taking (Anthropic also calls it agentic memory): the agent writes notes outside the context window and reads them back later (Anthropic engineering).

Anthropic's example: an agent playing Pokémon kept notes across thousands of steps, such as how long it had trained in one area; after a context reset it read its notes and continued (same article).

Analogy, with the mapping stated: the game-day whiteboard is the context window (everything visible now, wiped after the game); the season binder is stored notes (survives); flipping to the right binder page is loading memory. The binder does not flip its own pages: your program decides what to load.

Concrete example, for your assistant:

students/jsmith.json
{ "trained": ["laser_cutter", "3d_printer"],
  "pending": ["bandsaw"],
  "last_booking": "laser_cutter, 2026-11-12" }
  • At session start, the program loads that student's record (small) into context, or gives the model a get_training_status tool.
  • When a booking or training changes, a tool writes it back. Write only facts you will need again.
  • Do not save whole transcripts. They are big, noisy and re-bill on every call.

Retrieval: finding the right manual page 6 min

Big picture: a manual is too long to put in every call. So search first, then put only the best few passages into context. This is retrieval-augmented generation (RAG): fetch relevant material from a knowledge base and add it to the prompt (Anthropic: Contextual Retrieval).

First check the easy option: Anthropic notes that a knowledge base under about 200,000 tokens (roughly 500 pages) can go straight into the prompt with no RAG, and prompt caching makes that cheaper and faster (same post). Past that size, use retrieval.

  • Chunk: a piece of a document, usually a few hundred tokens or fewer. Each chunk is one searchable unit.
  • Embedding: a vector that encodes a chunk's meaning, stored in a vector database and searched by semantic similarity. Good at meaning, can miss exact strings.
  • BM25: an older keyword-ranking method that matches exact words. A query for an error code like "TS-999" is found by BM25 where embeddings may return general error pages. Combining both and merging the rankings works better than either (Anthropic).

For your assistant, that means: embeddings for "how do I stop the laser from charring plywood", BM25 for "error E-42" or a part number.

A common mix-up

"A chunk means the same thing alone as in the manual." It often does not. Anthropic's example: a chunk saying "revenue grew 3%" does not say which company or quarter. In your manuals, "set the speed to 40%" does not say which machine or material. The fix they describe: have a model write a short note on where each chunk fits and prepend it before indexing. They report that this cut top-20 retrieval failures from 5.7% to 3.7% (embeddings), to 2.9% with BM25 added, and to 1.9% with reranking (same post). Those numbers are from their tests, not yours.

Retrieval as a tool. You can give the model a search_manuals(query) tool, so it retrieves just in time, only when it decides it needs a page. Anthropic describes agents keeping lightweight references and loading content with tools when needed, slower than precomputed retrieval but without loading everything up front, and mixes of both (Anthropic engineering). The loop you already know does the work: the model calls the tool, the program runs the search, the chunks come back as a tool result.

Worked example and practice 8 min

Goal: predict cost per request. You need it to defend the budget.

Worked example: the problem

The assistant answers "Is the laser cutter free tomorrow at 3 pm, and do I need training?" It makes three tool calls, then writes the final answer.

  • Setup (system prompt, tool definitions, question): 2,050 tokens
  • Each model request for a tool: 50 tokens
  • Tool results: calendar 300, manual search 1,500, training record 100 tokens
  • Question: how many input tokens in total are sent across all four model calls? (Ignore the final answer, which is output.)
StepWhat happensWhy
1Call 1 input: 2,050Only the setup exists so far.
2Call 2 input: 2,050 + 50 + 300 = 2,400The program resends everything, plus the calendar request and result.
3Call 3 input: 2,400 + 50 + 1,500 = 3,950The manual result is added to the history.
4Call 4 input: 3,950 + 50 + 100 = 4,100The training result is added, and the model can now answer.
5Total: 2,050 + 2,400 + 3,950 + 4,100 = 12,500Each call is billed separately, and each call's input is the entire history.

Result: 12,500 input tokens, though the final context is only 4,100. Idea: cost is the sum of all inputs, so big results early are paid for repeatedly.

Apply it to the design review

Write down, in three bullets, what your assistant (1) keeps in context during a run, (2) saves between sessions, and (3) retrieves from the manuals. Then compare.

One reasonable answer
  • Context: system prompt, tool definitions, this chat, and only the top few retrieved chunks.
  • Saved: a small record per student (training status, last booking), loaded at session start.
  • Retrieved: manual chunks through a search_manuals tool, using keyword plus meaning-based search, with each chunk labelled with its machine and section.

Your team may choose differently, for example putting a short manual directly in the prompt. Be ready to justify it with size and cost.

Summary 2 min

  • The context window is everything the model sees on one call: system prompt, tools, history, tool results and its reply. More is not better: recall degrades as it fills.
  • Between steps, the program resends the whole history, so cost is the sum of every call's input.
  • Between sessions, nothing carries over unless the program saves notes to storage and loads them back.
  • For long manuals, retrieve a few relevant chunks (keyword plus meaning-based search, chunks labelled with their source) instead of resending everything.
