The context window: what the model sees 5 min

Start with an everyday case. You hire a helper who has no memory of anything, ever. Each time you want help, you hand them a single sheet of paper with everything they need written on it. They read the sheet, write a reply, and forget the whole exchange. If you want them to continue, you must hand over a new sheet that includes everything again.

A language model works like that helper. The context is the set of tokens the model reads when it writes a response (Anthropic, context engineering). A token is a small chunk of text, a word or part of a word. The context window is the limit on how much the model can work with in one call: Anthropic's documentation calls it the model's "working memory" and says it includes the response the model is writing (Claude docs, context windows).

What counts toward that limit? More than the chat. The docs list it: the system prompt, every message including tool results, your tool definitions, and the output the model generates. The system prompt is the standing instructions you write ("You are the makerspace assistant. Never book a machine unless the student is trained.").

Part of one requestMakerspace example
System promptRules, tone, opening hours
Tool definitionsDescriptions of check_calendar, search_manuals, book_machine
MessagesThe student's question, earlier turns, every tool result
The model's replyA tool request, or the final answer

The key fact for design: the model keeps nothing between calls. The program sends the whole context again each time. The docs say it plainly: each turn's input is all previous history plus the new message, and the model's output becomes part of the next input.

A common mix-up (M3)

"The assistant remembers me; I talked to it yesterday." It is tempting because chat apps feel continuous. But the model itself keeps nothing. Anything it appears to remember was put into its context again by the program, from a saved record. If your program does not save and reload it, it is gone.

Window sizes are large now: the docs list 1M tokens for many current models. That is room, not a reason to fill it, as section 4 shows.

Between steps: the context grows 5 min

Now connect this to the loop. In an agent, each step is a separate model call. After a tool runs, the program appends the tool's result to the context and calls the model again, and the new call receives everything so far. So inside one request, the context only grows.

Curating: more context is not better 4 min

If a bigger window were free and harmless, you could put all the manuals in every request and be done. It is neither. Costs add up as you just saw. And the model gets worse at using a very full context: the docs name this context rot: as token count grows, accuracy and recall degrade (Claude docs). Anthropic's engineers describe context as a finite resource with an "attention budget" that each new token uses up, and say the decline is a gradual slope, not a cliff (Anthropic). Their guiding aim: the smallest set of high-signal tokens that still gets the result you want.

A common mix-up (M7)

"The window is 1M tokens, so I can put everything in." It is tempting because the limit sounds like the only constraint. But cost repeats on every call, and quality can drop as the context fills. A big window is a safety margin, not a plan.

When a long task fills the window anyway, there are three standard moves from the same sources:

  • Clear old tool results. The lightest option: once the assistant has used a 6,000-token manual excerpt, the program can drop it. The docs call this tool result clearing, and the engineering post calls it the lightest form of compaction.
  • Compaction. The conversation is summarized and the agent continues from the summary. Claude Code, for example, keeps decisions and unresolved problems and drops redundant tool output (Anthropic). Some platforms do this on the server (compaction docs).
  • Sub-agents. A helper agent explores in its own clean context and returns a short summary, often 1,000 to 2,000 tokens, to the lead agent. You will meet this in the multi-agent lesson.

A summary is lossy: it can drop a detail you later need. That is why the next section matters.

Between sessions: notes as memory 5 min

Everything so far lives inside one request. When the session ends, or when compaction shrinks it, the context is gone. For things that must survive, such as "Dana completed laser cutter training on 3 March", the agent needs a memory outside the context. The simplest kind is notes: text written to storage that is not part of the window, then read back later. Anthropic calls this structured note-taking, such as a to-do list or a NOTES.md file, and shows an agent resuming multi-hour work after context resets by reading its own notes (Anthropic). Lilian Weng's survey of agents frames the same split: the context is short-term memory, and long-term memory is an external store the agent can query (Weng, LLM Powered Autonomous Agents).

Anthropic's memory tool shows the mechanism concretely. It is client-side: the model requests a file operation (view, create, edit, delete), and your application runs it against storage you control, returning the result as a normal tool result. When it is enabled, the model checks its memory directory before starting a task, and the system prompt tells it to assume its context could be reset at any moment, so progress should be saved as it goes (Claude docs, memory tool). This is the same agent loop you already know; memory is just another tool.

Memory is a design decision, so choose what to save. Save facts that will matter later and cannot be re-derived cheaply: training status, a student's stated preferences, a half-finished booking. Do not save bulky raw material you can fetch again, or things that go stale. The docs also list duties that fall on you: cap file sizes, expire old memory, and keep sensitive data out.

Retrieval: finding the right page 4 min

The second kind of outside memory is not written by the agent: it is a large body of reference text, like your machine manuals. You cannot load 400 pages into every request (section 3), so the agent needs retrieval: searching the store and putting only the best-matching pieces into context.

Anthropic describes this as just-in-time retrieval: instead of preloading everything, the agent keeps lightweight pointers, such as file paths or stored queries, and uses tools to load content when needed. The trade-off they name: it is slower than having everything ready, and the agent needs good guidance on how to search. They often recommend a hybrid, with a small amount loaded up front and the rest fetched on demand (Anthropic).

How does search find the right page? Two common approaches: keyword matching (like grep: find pages containing "kerf" and "acrylic"), and similarity search over embeddings, where each page is turned into a list of numbers so that pages with similar meaning sit close together (Weng's post mentions external vector stores with fast retrieval as the usual way to do this). You do not need the math, which is out of scope. You need the design consequence: retrieval is a tool. Its description tells the model when to use it, and its output is what lands in context, so a tool that returns three well-chosen pages is far cheaper than one that returns thirty.

Worked example and practice 7 min

Now put it together twice: first estimate the cost of a request, then place information in the right home.

Worked example: total input tokens

The system prompt is 1,500 tokens, the tool definitions 1,000, and the student's question 50. The assistant calls check_calendar (result 300 tokens), then search_manuals (result 6,000), then check_training_record (result 200), then answers. Each tool request the model writes is 100 tokens. How many input tokens are processed in total, across all four calls?

  1. Base context: 1,500 + 1,000 + 50 = 2,550. This is call 1's input.
  2. Call 2 input = base + the model's first request + calendar result = 2,550 + 100 + 300 = 2,950. The new call re-sends everything.
  3. Call 3 input = 2,950 + 100 + 6,000 = 9,050.
  4. Call 4 input = 9,050 + 100 + 200 = 9,350. The final answer is output, not input.
  5. Total = 2,550 + 2,950 + 9,050 + 9,350 = 23,900 input tokens.
  6. Check: the biggest result entered at call 3, so it was counted in calls 3 and 4. A result added later is counted fewer times.
Your turn: estimate

Same prompt, tools and question (base 2,550), same 100-token requests. This time the order is: check_calendar (result 300), then check_training_record (result 200), then search_manuals (result 4,000), then the answer. Call 1 is 2,550. Work out the input of calls 2, 3 and 4, then the total.

Show a solution

Call 2 = 2,550 + 100 + 300 = 2,950. Call 3 = 2,950 + 100 + 200 = 3,250. Call 4 = 3,250 + 100 + 4,000 = 7,350. Total = 2,550 + 2,950 + 3,250 + 7,350 = 16,100 input tokens. The big result came last, so it was re-sent only once. In general, fetching small things first and large things last is cheaper, when the order is free to choose.

Worked example: where does it live?

Decide a home for "Dana finished laser cutter training on 3 March".

  1. Is it needed only for this request? No: it matters at every future visit, so it cannot live in context alone.
  2. Is it a large reference text to search? No: it is one short fact about one person.
  3. So it is a note or record, stored outside, keyed by student, read by a tool such as check_training_record at the start of a booking request.

(4) Context for now, then clear it: it is cheap to fetch again, so after use it should leave the context and stay in the store.

Summary 2 min

  • The model keeps nothing between calls. The context window is everything the program sends in one request: system prompt, tool definitions, messages, tool results, and the reply.
  • Between steps, the context grows and is re-sent, so each tool result is paid for again in every later call. More context is not better; recall can degrade as it fills.
  • Between sessions, nothing survives unless you store it. Notes hold small facts to resume from; compaction and clearing keep a long task inside the window.
  • Retrieval is a tool that searches a large store and returns only the best few pieces, so the manuals stay outside and only what is needed comes in.
