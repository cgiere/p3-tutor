Context and memory: what an agent sees, keeps and looks up

By the end of this lesson you can decide, for each piece of information in the makerspace assistant, whether it belongs in the model's context, in saved notes between sessions, or in a store the assistant searches only when needed.

Objective O3: context and memory in an agent About 30 minutes Builds on the agent loop (learning record 0002)
Why this matters for you

Your assistant must answer from long machine manuals and remember each student's training status between visits, all on a small budget. Both jobs are memory decisions, and every token you put in front of the model costs money. At your design review you will be asked what the assistant keeps, what it saves and how it finds the right page. This lesson gives you the answers.

Warm-up 3 min

Recall

From the agent loop: the student asks "Is the laser cutter free tomorrow?" and the model decides to check the calendar. Say, in a sentence or two, who actually runs the calendar lookup, and where the result goes next.

Check your answer

The program around the model runs the lookup, because the model only writes a request naming the tool and its arguments. The program then sends the result back to the model, which is called again. That second part is today's topic: "sent back to the model" means the result is added to the text the model reads next. What exactly is in that text, and what happens to it as the loop goes on, is context.

Here is the plan. We follow one request through the assistant and watch what the model can see at each step. Then we ask what survives when the conversation ends. Last, we look at how the assistant can find one page in a manual that is far too long to read every time.

The context window: all the model sees 6 min

A concrete case first

Imagine a student on Monday asks the assistant, "How do I change the blade on the band saw?" The assistant answers. Ten minutes later the same student types, "And how tight should it be?" The assistant answers correctly: it knows "it" means the blade. How?

Not because the model remembered. A language model does not change when you talk to it. Each time the program calls it, the program sends everything the model should know as one block of text, and the model writes the next piece of text. The "memory" of the earlier question exists only because the program pasted it into the block again.

That block is the context: all the text sent to the model in one call. The model can only use what is in it. The context window is the maximum size of that block, counted in tokens, the small chunks of text (roughly three-quarters of an English word each) that models read and write. If the context is full, something has to leave before anything else can come in.

Notice what is in the box besides the chat: the system prompt (the standing instructions you write) and the tool descriptions from the last lesson. They are sent on every call. They are part of the context, and they take up room and money before the student has typed anything.

A common mix-up

"The model remembers our earlier conversation." This is tempting because chatbots feel like they remember. But the model is the same after every call; the program re-sends the history. If your program sends only the newest message, the model has no idea what "it" refers to. Remembering is something your program does, so you decide what is kept.

A common mix-up

"A bigger window means we can stop worrying about context." A bigger window raises the ceiling, but Anthropic's engineers describe context as a finite resource with diminishing marginal returns: as the window fills, the model's recall of details can get worse, which they call context rot, and you pay for every token you send (Anthropic, Effective context engineering for AI agents). Their goal is the smallest set of high-signal tokens that gets the job done.

Between steps: the context grows, and so does the bill 7 min

Inside one request, the agent loop calls the model several times. What is kept from one step to the next? Everything the program chooses to resend. In the usual design, that is the whole history: the question, each tool request the model wrote, and each result that came back. Each call's context is the previous call's context plus the new material.

That has a cost consequence you can calculate. Model usage is billed mostly by tokens, and every call is billed for the whole context it carries, including the parts it carried last time. Long tool results are especially expensive, because they ride along on every later call.

Worked example: the token bill for one request

The student asks, "Is the laser cutter free tomorrow at 3 pm, and do I need training?" The assistant makes three tool calls and then answers. The numbers below are made up but realistic in shape. The system prompt and tool descriptions together are 1,500 tokens. Each tool request the model writes is 50 tokens. The calendar result is 250 tokens, the manual page is 3,000, the training record is 100.

  1. Call 1. Input: 1,500. The model asks for the calendar.
  2. Call 2. Input: 1,500 + 50 (its request) + 250 (the result) = 1,800. It asks for the manual search.
  3. Call 3. Input: 1,800 + 50 + 3,000 = 4,850. It asks for the training record.
  4. Call 4. Input: 4,850 + 50 + 100 = 5,000. It writes the final answer.
  5. Total input billed: 1,500 + 1,800 + 4,850 + 5,000 = 13,150 tokens. The 3,000-token page was paid for twice, in calls 3 and 4.

Now suppose the search tool returned only the relevant 800-token section instead of a whole page. Call 3 becomes 2,650 and call 4 becomes 2,800, so the total is 1,500 + 1,800 + 2,650 + 2,800 = 8,750 tokens, about a third less, for the same answer.

So three things are true of what is kept between steps. First, the model keeps nothing itself; the program resends the context. Second, the context only grows during a request, and cost grows with it. Third, you control the growth: keep tool results short, and drop or shrink old results the model no longer needs. Anthropic describes clearing old tool results as one of the lightest forms of compaction, the practice of summarizing a conversation that nears the limit and starting a new window from the summary (Anthropic).

Providers may discount repeated, unchanged prefixes of a context, so exact pricing differs. The direction does not: bigger contexts cost more and dilute attention. Check your provider's pricing before you size your budget.
Check yourself

The search tool in the example above returns 3,000 tokens in call 3. Which change cuts the total input across the remaining calls the most?

Show the answer

The first option. Input cost is context size summed over calls, so the biggest lever is keeping large results out of the context.

Between sessions: nothing is kept unless you save it 6 min

A session here means one conversation or run, from the first message to when it ends. When it ends, the context is simply gone. Next Tuesday the student returns, and the model starts with a fresh context: the system prompt, the tools and the new message. It does not know the student passed the laser cutter training on Monday.

If the assistant should know that, your program has to save it somewhere outside the context, and load it into the context at the start of the next session. That outside place is the assistant's long-term memory. The memory inside one conversation, the message history, is its short-term memory. LangChain's documentation draws the same line: short-term memory is scoped to one conversation thread, and long-term memory persists across threads and sessions, stored as JSON documents under a namespace and a key (LangChain, memory concepts).

Notes as memory

The simplest long-term memory is notes: short facts written to a file or database record. Anthropic calls this structured note-taking, or agentic memory: the agent regularly writes notes to storage outside the context window and reads them back later, such as a to-do list or a NOTES.md file (Anthropic). That is exactly how this tutor works: it reads NOTES.md at the start of every session, because it remembers nothing between them.

Two design questions matter for your assistant. What to save: short, durable facts that will be useful later, such as "Sam completed laser cutter training on 12 Oct" or "Sam prefers evening slots". Do not save whole transcripts, because loading them back would refill the context. Who writes the note: either the model, through a "save note" tool, or your own program, which writes a record whenever a fixed event happens, such as a training sign-off. For something as important as training status, a fixed program step is safer than hoping the model remembers to save it.

A common mix-up

"Saved notes are automatically in the model's context." A note in a file does nothing until your program loads it. Saving and loading are separate steps, and loading costs tokens every time, so load only what the current request needs, such as this student's record, not every student's.

Retrieval: finding the right page 6 min

Now the manuals. Suppose the combined manuals run to 400 pages, roughly 200,000 tokens. Putting them all in the context for every question would be slow, expensive and, per the context rot point above, likely to make answers worse. Yet the answer to "how tight should the blade be?" sits on one page.

Retrieval means fetching only the relevant pieces from a larger store at the moment they are needed, and putting just those into the context. The manuals become another store, like the notes, and a search tool is the way in. A typical setup has three parts:

  1. Split each manual into chunks, short passages such as a section or a few paragraphs, each labelled with its machine and page.
  2. Search the chunks for the ones that match the question. One way is keyword search; another is to compare embeddings, numbers computed from text so that passages with similar meaning get similar numbers. You do not need the math: you need to know that embedding search finds "tension" when the student writes "how tight".
  3. Return the top few chunks to the model as a tool result, with their page references, so the model can answer and cite.

This is where retrieval meets the agent loop. In a design that retrieves before the model runs, the program fetches chunks first and puts them in the context. In a design where the model itself calls a search tool, the model decides when and what to search, and can search again if the first results miss. Anthropic calls the second style just-in-time retrieval and notes it is slower and needs good guidance, so a mix is often best: some facts always loaded, others fetched on demand (Anthropic). For you, a sensible starting mix is the system prompt with safety rules always loaded, and manual pages fetched by a search_manuals tool.

A common mix-up

"Retrieval means the model reads the whole manual and picks the page." That would be the expensive thing retrieval avoids. The search step runs in your program, outside the model, and the model sees only the chunks it returns. The consequence: if the search returns the wrong chunk, the model never sees the right page, however smart it is. Retrieval quality is a design problem you own.

Two things make retrieval work well. First, chunk with care: a chunk cut mid-procedure, such as steps 1 to 3 without step 4 ("lock the guard"), can produce an unsafe answer. Second, write the tool description well, as you learned for tool calling, so the model knows to search with specific terms such as "band saw blade tension" and not "help".

Worked example and practice 5 min

Now put the three places together: the context, saved notes and a searchable store.

Worked example: where does each fact live?

Decide for each item whether it is always in context, saved notes loaded at session start, or retrieved on demand.

  1. "Never operate machines unsupervised if untrained." Always in context (the system prompt). It applies to every request, it is short, and the model must never miss it.
  2. Sam's laser cutter training sign-off. Saved notes, loaded at session start for Sam only. It must survive between sessions and is short, but it is useless for other students.
  3. The band saw blade-change procedure, page 47. Retrieved on demand. It is long, only needed for some questions, and the whole manual is far too big to load.
  4. The last three messages of this chat. Always in context, as short-term memory. Without it, "it" and "the other blade" mean nothing.

The test for each: does it apply to every request (always in context), does it have to outlive the session (notes), or is it big and only sometimes needed (retrieval)?

Your turn

Place these two items with the same test. First: "Sam prefers evening time slots." Second: a calendar lookup that returned 40 entries, 35 of which are for other machines. Hint for the second: the loop resends results, so think about size, and about what the model needs from it.

Show a solution

The preference is saved notes: it must outlive the session, it is tiny, and it is specific to Sam. The 40-entry result does not belong in any memory as it stands. It is a tool result, so it sits in context and gets resent on every later call. Better: make the calendar tool filter by machine and date so only the relevant 5 entries come back, which keeps the context small and the bill down.

Summary 2 min

  • The model sees only its context: the text sent in one call. It remembers nothing by itself; your program decides what is resent.
  • Within a request, the context grows with every step, and you pay for the whole of it on every call, so keep tool results short.
  • Between sessions, nothing survives unless saved to notes and loaded back in; save short durable facts and load only what the request needs.
  • For long sources such as manuals, use retrieval: split, search, and put only the best few chunks in the context.

Say it in your own words: without looking, explain to a teammate why the assistant needs three places for information (context, notes, a searchable store) and not one big prompt.
