Context and memory: what an agent sees, keeps and looks up

By the end of this lesson you can decide, for each piece of information in the makerspace assistant, whether it belongs in the model's context, in a saved note, or in a manual you retrieve from, and say why.

Why this matters for you

Your assistant must answer from long machine manuals, remember each student's training status between visits, and stay inside a small model budget. All three are decisions about context and memory, and you will defend them at your design review.

Warm-up 2 min

Recall

Without scrolling up: in the agent loop, who runs a tool, the model or the program around it? And what does the program do with the result?

Check your answer

The program runs the tool. The model only writes a request that names the tool and its arguments. The program then sends the result back to the model as part of its next input and calls the model again. That last step matters today: the result goes into what the model reads next, so the question becomes what the model reads, and for how long it stays there.

The context window: the model's desk 5 min

Start with an example. A student types: "Is the laser cutter free tomorrow at 3 pm?" Your program sends the model some text: the assistant's instructions, the descriptions of its tools, and the question. The model writes a reply. That text you sent is everything the model knows about this request. It has no other view of the makerspace.

The general idea: the context window is the set of tokens the model reads when it produces its next output. A token is a small chunk of text, often a word or part of one. The window has a maximum size, and everything the model should use has to fit inside it: instructions, tool descriptions, the conversation so far, tool results and any pages you retrieved.

A good picture is a desk. The model can only work with what is on the desk right now. Anthropic's engineers describe it in similar terms: context is a finite resource with diminishing returns, because the model has an "attention budget" that every added token uses up.

Two facts follow, and both bite your budget.

  • Size. If a manual does not fit on the desk, the model cannot read it all.
  • Quality. Even when everything fits, more is not better. Anthropic calls the decline context rot: as the window fills, the model's ability to accurately recall information from it gets worse. So the aim is the smallest set of useful tokens, not the most tokens.
You pay for tokens, so a smaller desk is also a cheaper desk. Good context choices and a small budget pull in the same direction.
Check yourself

A teammate says: "Our model's window is huge, so we can paste all twelve machine manuals into every request and skip the design work." What is the best reply?

Show the answer

The third option. Fitting is not the test; the budget and the quality of recall are.

What is kept between steps 5 min

Now the agent loop from your last session. Each pass through the loop is a separate model call. Here is the question that matters: when the model is called the second time, does it remember the first?

It does not. The model keeps nothing between calls; each call starts fresh and reads only what you send ("models are stateless"). What looks like memory inside a single request is your program doing bookkeeping: after each step it appends the model's tool request and the tool's result to the conversation, then sends the whole thing again.

This has two consequences for your design.

  1. Everything on the desk is paid for again at every step. A long manual page returned at step 2 is also read, and billed, at step 3, step 4 and so on.
  2. A long request fills its own window. An agent that explores for many steps can run out of room, or hit context rot, before it finishes.

When a loop is nearing the limit, the standard fix is compaction: summarize the conversation so far and start a fresh window with that summary. Anthropic describes it as keeping decisions and unresolved problems while discarding redundant tool output, and notes that clearing old tool results is the lightest version. For a makerspace question that takes three or four steps you will rarely need it. Know it exists for later.

A common mix-up

"The model remembers the earlier steps, because it is the same conversation." It feels true because a chatbot seems to remember. But the program resends the earlier steps each time. If your program forgot to append a tool result, the model would not know the tool had ever run, and it would likely ask for the same tool again. That is also one cause of the stuck loop from quiz 0001.

Check yourself

Your assistant's loop runs five model calls for one request. A 2,000-token manual page arrives after call 2. Roughly how many times is that page read by the model?

Show the answer

Three times: calls 3, 4 and 5, because the program re-sends it with every later call.

What is kept between sessions: nothing 4 min

A session is one conversation or request, from the first message to the end. If a student visits on Monday and again on Friday, those are two sessions.

If steps do not remember, sessions certainly do not. At the end of a session the window is thrown away. On Friday the model starts with an empty desk, plus whatever your program puts there. It has no idea that the student passed laser cutter training on Monday unless your program saved that fact somewhere and loaded it back in.

This gives the clearest rule in the lesson:

The model has no memory. Your program has memory. Anything the assistant "remembers" is text that something outside the model stored, and that your program put back on the desk.

There are two ways to put it back, and they are the two halves of the rest of this lesson. Retrieval looks up stored material that you wrote ahead of time (manuals) and brings in the relevant part. Notes are facts the assistant saves as it goes (a student's training status) and reads later.

A common mix-up

"A bigger context window gives the assistant memory." A bigger window only gives more room within one session. When the session ends, the window is gone, however large it was. Memory between sessions needs storage outside the model, such as a file or a database. The Machine Learning Mastery article states it directly: continuity must come from external storage.

Check yourself

On Monday the assistant tells a student: "You are now cleared for the 3D printers." On Friday the same student asks, "Am I cleared?" and nothing was saved. What happens?

Show the answer

The first option: the model cannot know. Only your program can carry Monday's fact into Friday.

Retrieval: finding the right page 6 min

Back to the manuals. A student asks, "What speed should I use to cut 6 mm acrylic on the laser cutter?" The answer is in one paragraph of a 90-page manual. You do not want to put 90 pages on the desk for one paragraph.

Retrieval means searching a stored collection for the few pieces relevant to the current question, and putting only those on the desk. The usual setup splits each manual into chunks (a few paragraphs each), and finds the chunks that best match the question. This is often called retrieval-augmented generation, or RAG.

There are two ways to wire it in, and Anthropic describes both:

StyleHow it worksFor the makerspace
Up frontThe program searches before the model is called and puts the top chunks in the first prompt.Simple and fast; one model call can answer.
Just in timeThe model gets a search_manuals tool and calls it when it decides it needs a page.Flexible; costs extra steps, and the tool needs a good description.

Anthropic's article calls the second approach just-in-time retrieval, and notes that runtime exploration is slower than retrieving up front. Its own coding agent mixes the two. Your quiz 0001 assistant already had a search_manuals tool, so it is just-in-time.

A common mix-up

"Retrieval always returns the right page." It returns the pages that look most similar to the question, which is not the same. A search can return an old version of a rule next to the new one, and the two chunks may contradict each other. The Machine Learning Mastery article suggests resolving such conflicts before generation, for example by preferring the most recent. For you: keep manual versions dated, and test retrieval on real student questions before you trust it.

Check yourself

Retrieval for "cut speed for 6 mm acrylic" brings back the laser's safety chapter instead of the settings table. Which fix attacks the real cause?

Show the answer

The third option. The model can only use what retrieval puts in context, so retrieval itself must be tested and improved.

Notes: memory you write yourself 4 min

Manuals are written by people ahead of time. But some facts only appear while the assistant works: "Sam passed laser cutter training on 4 March", or "Sam prefers evening bookings". For these, the assistant needs to write as well as read.

The idea is called structured note-taking, or agentic memory in Anthropic's article: the agent writes notes to storage outside the context window and reads them back later. In their examples a coding agent keeps a to-do list or a NOTES.md file, and an agent playing a game kept maps and strategy notes so it could carry on after its context was reset.

For your assistant this is just two more tools: save_note(student_id, text) and read_notes(student_id), backed by a file or a small database. Your program loads that student's notes at the start of a session, so Friday's desk contains Monday's fact.

Student notes: sam_0412
- 2025-03-04  Passed laser cutter training (staff: J. Ortiz)
- 2025-03-04  Booked laser, Fri 15:00-16:00
- Prefers afternoon slots

Three rules keep notes useful and cheap:

  • Save facts, not transcripts. A short line costs few tokens each time it is loaded. A whole old chat costs many, every session.
  • Keep the authority outside the model. Training status is a record that should come from the training database, not from a note the model wrote from memory. A note can say "passed training"; a lookup can confirm it.
  • Decide what is safe to save. These are student records. Store only what the assistant needs, and ask your advisor about privacy rules.
The same article mentions that Anthropic has released a file-based memory tool in public beta. You do not need one to start: a text file per student works for a design prototype.
Check yourself

Which of these is the better thing for the assistant to save as a note for a student's next visit?

The second option: short, specific and useful later.

Worked example and practice 3 min

Here is the lesson's skill in use: tracing what the desk holds and what it costs. The numbers are made up to keep the arithmetic easy. Count input tokens only, meaning what the model reads on each call.

Worked example

A student asks, "Is the laser free tomorrow at 3 pm, and do I need training?" The start of the context (instructions, tool descriptions and the question) is 1,500 tokens. The model makes three tool requests of 50 tokens each. Results: calendar 300 tokens, manual page 2,000 tokens, training record 150 tokens. A fourth call writes the answer. How many input tokens in total?

  1. Call 1 reads only the start: 1,500.
  2. Call 2 reads the start, the first request and its result: 1,500 + 50 + 300 = 1,850.
  3. Call 3 adds the second request and the manual page: 1,850 + 50 + 2,000 = 3,900.
  4. Call 4 adds the third request and the training record: 3,900 + 50 + 150 = 4,100.
  5. Total: 1,500 + 1,850 + 3,900 + 4,100 = 11,350 input tokens. The 2,000-token page is only 2,000 tokens of "new" text, but it is read twice, so it accounts for 4,000 of the total.
Your turn

A different request: the start is 1,000 tokens; the model makes two tool requests of 50 tokens each; the first result is a training record of 100 tokens, the second a manual page of 3,000 tokens; a third call writes the answer. Call 1 reads 1,000 tokens. Work out calls 2 and 3 and the total. Then redo call 3 and the total if retrieval had returned an 800-token excerpt instead of the full 3,000-token page.

Show a solution

Call 2 = 1,000 + 50 + 100 = 1,150. Call 3 = 1,150 + 50 + 3,000 = 4,200. Total = 1,000 + 1,150 + 4,200 = 6,350 input tokens. With the 800-token excerpt, call 3 = 1,150 + 50 + 800 = 2,000, and the total = 1,000 + 1,150 + 2,000 = 4,150. The excerpt cuts the cost by about a third, and that saving repeats in every request that retrieves a page.

Apply it to your assistant

For each item, say whether it goes in the context at every call, is retrieved when needed, or saved as a note: (a) the rule "never book a student without current training"; (b) the full text of the band saw manual; (c) Sam's training status. Then compare with the suggestions.

Show suggestions

(a) Always in context, in the instructions: it is short and applies to every request. (b) Retrieved when needed: it is long and relevant to only some questions. (c) Stored outside the model (a note, or better a lookup in the training records), and loaded for that student at the start of a session.

Summary 1 min

  • The context window is the desk: the model reads only what is on it, and every token on it costs money and can crowd out the useful ones.
  • Between steps, the program keeps things by re-sending them; the model keeps nothing, so the desk grows and every call pays for all of it.
  • Between sessions, nothing survives unless something outside the model saved it and your program loaded it back.
  • Retrieval brings in the relevant part of a large store; notes let the assistant save new facts. Both are tools your program provides.

Say it in your own words: without looking up, explain to a teammate why the assistant can answer a question about Monday's booking on Friday. Where is the fact stored, and how does it get back in front of the model?
