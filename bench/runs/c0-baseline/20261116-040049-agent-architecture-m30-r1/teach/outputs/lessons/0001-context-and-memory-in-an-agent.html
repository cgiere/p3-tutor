Context and memory in an agent

By the end of this lesson you can decide, for each piece of information in the makerspace assistant, whether it belongs in the model's context, in saved notes, or in a manual store that is searched on demand, and you can say why.

Objective O3: context and memory in an agent About 30 minutes Builds on your work on the agent loop (quiz 0001)
Why this matters for you

Your assistant must answer from long machine manuals, and it must remember each student's training status from one visit to the next. Both are context-and-memory decisions, and both decide how much each request costs on a small model budget. This is the lesson behind the design-review question "what does the assistant keep, and where?"

The context window: what the model sees 6 min

Start with a concrete case. A student types: "Is the laser cutter free tomorrow, and do I need training?" Your program calls the model. What does the model receive?

It does not receive the question alone. It receives one long block of text made of:

  • the system prompt: your standing instructions ("You are the makerspace assistant. Be brief. Never book without confirming.");
  • the tool definitions: the name, description and parameters of check_calendar, search_manuals and the rest;
  • the conversation so far: the student's messages, the model's earlier replies, every tool request and every tool result.

All of this together is the context: the text the model is given for one call. The context window is the limit on how much text the model can take in and produce in one call. The Claude documentation describes it as the model's "working memory", and says that everything in the request counts toward it: the system prompt, every message including tool results, and the tool definitions; the output the model writes counts too (Claude docs, Context windows). Text is measured in tokens, small pieces of text, roughly a short word or part of a longer word. The window is a limit in tokens, and, as you will see, tokens are also what you pay for.

The model keeps nothing between calls

This is the most important fact in the lesson. The model itself does not remember the previous call. Each call starts blank, and the program must send everything the model should know, every time. The docs describe it this way: each turn's input holds all the previous history plus the new message, and the output then becomes part of the next turn's input (Claude docs).

So the "memory" of a conversation is a list your program keeps and re-sends. Here is the idea in Python, in the shape you will write soon:

messages = [{"role": "user", "content": question}]
while True:
    reply = call_model(system_prompt, tools, messages)   # sends EVERYTHING
    messages.append(reply)                               # the list grows
    if reply is final_answer:
        break
    result = run_tool(reply)                             # your program runs it
    messages.append(tool_result(result))                 # the list grows again

The list messages is the context's growing part. Nothing in the model "remembers" it; the list is re-sent on every pass through the loop.

Token counts here are made-up round numbers to show the shape. Your real counts depend on your prompt and manuals; the API reports what each request used, and a token-counting API can estimate before you send (Claude docs).
A common mix-up

"The model remembers the conversation." It is tempting because chat apps feel like talking to someone who remembers. But what you are talking to is a program that re-sends the whole transcript every time. If your program forgot to include an earlier message, the model would behave as if it never happened.

Bigger is not better: cost and context rot 5 min

Current Claude models have large windows: the docs list up to 1 million tokens for many of them (Claude docs). Does that mean you can paste every machine manual into the system prompt and be done? Two problems say no.

Problem 1: you pay for every token, at every call

Because each call re-sends the context, a long context is paid for again and again. Here is the run from Figure 1, step by step. It is illustrative, but the arithmetic is real.

Worked example: counting input tokens

The system prompt and tools are 2,000 tokens. The question is 100 tokens. Each tool request the model writes is 100 tokens. Results: the calendar returns 400 tokens, the manual search returns one page of 3,000 tokens, and the training check returns 200 tokens.

  1. Call 1 sends 2,000 + 100 = 2,100 tokens. The model requests check_calendar.
  2. Call 2 sends call 1's input, plus the 100-token request, plus the 400-token result: 2,100 + 100 + 400 = 2,600.
  3. Call 3 sends 2,600 + 100 + 3,000 (the manual page) = 5,700.
  4. Call 4 sends 5,700 + 100 + 200 = 6,000. The model writes the final answer.
  5. Total input over the request: 2,100 + 2,600 + 5,700 + 6,000 = 16,400 tokens, though the longest single context was only 6,000.

The 3,000-token page was sent in call 3 and call 4. Whatever enters the list is paid for in every later call.

Now suppose the search had returned three pages (9,000 tokens) instead of one. Call 3 would send 11,700, call 4 would send 12,000, and the total would be 28,400: the same request costs about 1.7 times as much. For a small budget, what you let into the list is your main cost control.

Prompt caching can make the repeated, unchanging start of a context cheaper to resend. But the docs are explicit that cached tokens still occupy the window: caching changes what you pay for them, not whether they count (Claude docs).

Problem 2: context rot

More text does not mean better answers. The Claude docs say that as token count grows, accuracy and recall degrade, a phenomenon called context rot, which makes curating what is in context as important as how much space is available (Claude docs). Anthropic's engineering team describes context as a finite resource with diminishing returns, with an "attention budget" that every new token draws on, and says the goal is the smallest set of high-signal tokens that makes the result you want likely (Anthropic, Effective context engineering). The same article says this is a gradual decline, not a cliff.

An everyday comparison: a technician who is handed one page of the laser cutter manual can find the answer. A technician handed a 2,000-page binder and the same question can too, but slowly, and is more likely to grab the wrong page.

A common mix-up

"A bigger window means I can skip the design work." It is tempting because the limit sounds like the only constraint. But the window is a ceiling, not a target. Fitting all the manuals in is possible and still a bad idea: you pay for them at every call, and the model finds answers less reliably in a crowded context.

What is kept between steps 5 min

Between steps of one request, the program keeps the message list, and by default it keeps all of it. That is simple and safe: the model can always look back at what it did. But Figure 1 shows the cost of that default, and in a long task the list can approach the window's limit. Three tools manage it, from lightest to heaviest.

TechniqueWhat it doesMakerspace use
Keep it allNothing removed; the list only grows.Fine for short chats: a few tool calls and small results.
Clear old tool resultsDrop or shorten bulky results once the model has used them.After the model has read a 3,000-token manual page and noted the answer, the page is no longer needed.
CompactionSummarize the conversation and continue in a fresh window that starts from the summary.A long booking chat that nears the limit.

Anthropic describes compaction as summarizing a conversation that is nearing the limit and starting a new window with the summary, keeping things like decisions and unresolved problems while discarding redundant tool output; it calls clearing old tool results one of the lightest-touch forms of compaction (Anthropic, Effective context engineering). The API docs also offer server-side compaction and tool-result clearing as ready-made options (Claude docs).

The trade-off is always the same: whatever you remove can no longer help the model, and a summary can lose a detail that mattered. So summarize the way you would hand over a shift: what was decided, what is still open, and nothing else.

What is kept between sessions: notes 6 min

Now the second kind of "between". A student finishes their chat on Tuesday. On Thursday they open a new chat. The message list from Tuesday is gone: your program started a new, empty list. The model knows nothing about Tuesday. Yet your assistant should still know that this student passed the laser cutter safety course.

The fix is plain: save it outside the context, and load it back in when needed. Anthropic calls this structured note-taking, or agentic memory: the agent writes notes to storage outside the context window and reads them back later, such as a to-do list or a NOTES.md file. Their example is an agent playing a game across thousands of steps, keeping its own maps and notes so that it could continue after its context was reset (Anthropic, Effective context engineering). Claude also has a file-based memory tool, which the docs point to for agents that span several sessions.

So "memory" in an agent is not something inside the model. It is a file or database your program owns, plus two habits: write the important facts, and read the right ones at the start of the next session.

A worked design: the training record

For the makerspace, what should be saved about a student? Apply two tests. First, will a future session need it? Second, can it be looked up reliably another way? The student's training status is needed later, and it is best stored as a small, exact record, not as a chat summary:

{"student_id": "s4821",
 "trained": ["laser_cutter", "3d_printer"],
 "pending": ["cnc_router"],
 "last_visit": "2026-11-12"}

At the start of a session the program reads this record (a few dozen tokens) and puts it into the context. It does not load the transcript of the last six chats. Casual chat history is rarely worth saving; exact facts the assistant will need are.

The same record might also be the output of a check_training_record tool. Whether to preload it or let the model call the tool when asked is a real design choice, and the next section gives you a way to decide it.
A common mix-up

"A big enough window gives the assistant memory." It is tempting because within one chat a long context behaves like memory. But the window only holds what your program sends in that request. When Thursday's chat starts with an empty list, it does not matter how large the window is: nothing from Tuesday is in it unless you saved it and loaded it.

Retrieval: finding the right page 6 min

The manuals are too big to keep in context and too useful to leave out. The answer is retrieval: keep the manuals in a store, find the few pages that matter for this question, and put only those into the context. This is the third box in Figure 2.

Take the question "How do I change the focus lens on the laser cutter?" There are two broad ways to find the page.

Retrieve up frontRetrieve just in time
HowBefore calling the model, your program searches the manuals for the question and adds the best matches to the context.The model gets a search_manuals tool and a list of manual titles, and fetches pages itself as it needs them.
StrengthFast: one model call, and the page is there already.Flexible: the model can search again with better words, or open a second manual.
WeaknessIf the search misses, the model never sees the right page and cannot ask for it.Slower and more calls, and a poorly guided model can waste context on dead ends.

Anthropic describes the same split: classic approaches surface context with embedding-based retrieval before the model runs, while "just in time" agents keep lightweight identifiers such as file paths, stored queries or links, and load data at runtime with tools. It also notes the slowness and the risk of dead ends, and describes a hybrid: load some data up front for speed and let the agent explore further as needed, with the advice to "do the simplest thing that works" (Anthropic, Effective context engineering).

Two details that decide whether retrieval works

Cut the manuals into pages or sections that each make sense alone, and give each a clear title. If the unit is a whole 200-page manual, retrieval returns a whole manual and you are back to the cost problem. If it is a single sentence, the answer may be missing its warning.

Return only the best few results, and tell the model where each came from (manual and section) so it can cite it or ask for the next page. Anthropic's note on metadata applies: names, folders and timestamps help an agent judge what is relevant (Anthropic, Effective context engineering). For students, a cited section is also easier to trust than a confident paragraph with no source.

How the search itself works, by keywords or by comparing meaning, is a later topic. For now, treat search_manuals as a tool in your loop like any other: it returns text that lands in the message list, and so it obeys everything you learned about cost and clearing.

A common mix-up

"Retrieval means the model learns the manuals." It is tempting because the answer afterwards is correct. But nothing is learned: the page was only placed in the context for that request. Next request, it is gone unless retrieved again. This is also why retrieval can fix the outdated facts you noticed in chatbots: update the manual store, and the next answer changes, with no training.

Worked example and practice 8 min

Worked example: where does each fact go?

For the makerspace assistant, decide where each item below lives: C (in the context for every call), N (saved notes, loaded at session start), M (manual store, retrieved on demand).

  1. "Be brief and never book without confirming." This is needed in every call and is short, so it goes in C, as the system prompt.
  2. The step-by-step procedure for changing a laser lens. It is long, rarely needed, and the same for everyone, so it goes in M, retrieved when asked.
  3. "This student is cleared for the laser cutter and 3D printer." It is small, exact, specific to one person and needed across sessions, so it goes in N. At session start it moves into C as a few lines.
  4. The 3,000-token page just read to answer a question. It entered C as a tool result. Once used, clear it or replace it with a short note, to stop paying for it.

The pattern: short and always needed goes in the context; exact and personal goes in notes; long and sometimes needed goes in a store you search.

Your turn: cost

Use the numbers from the worked example in the cost section: calls with 2,100, 2,600, 5,700 and 6,000 input tokens. Suppose that right after call 3, the 3,000-token manual page is replaced by a 300-token note, before call 4. How many input tokens does call 4 send, and what is the total over all four calls? Start from call 4's earlier size of 6,000.

Show a solution

Call 4 loses 3,000 tokens and gains 300: 6,000 − 3,000 + 300 = 3,300. The total is 2,100 + 2,600 + 5,700 + 3,300 = 13,700, down from 16,400. In a longer chat, with many more calls after the page, the saving would be larger, because the page would have been paid for at every one of them.

Your turn: design

Place each of these as C, N or M, and say why in one phrase, before opening the solution: (a) the booking rules, such as "maximum two hours per booking"; (b) the student's name and the machines they have been cleared for; (c) the 80-page CNC router manual; (d) the calendar result for tomorrow just returned by check_calendar.

Show a solution

(a) C if the rules are short and apply to every request, so they sit in the system prompt; if they ran to pages, they would move to M. (b) N: small, exact, personal, needed across sessions; loaded into C at session start. (c) M: long, sometimes needed, the same for everyone. (d) C, as a tool result, for as long as the booking conversation needs it. It is also stale quickly, so never save it in notes: tomorrow's calendar will have changed, and the tool should be called again.

Summary 2 min

  • The model keeps nothing between calls. The context, made of the system prompt, tools and the whole message list, is re-sent at every call, so it is paid for every time.
  • A bigger window is a ceiling, not a goal. Long contexts cost more and, through context rot, recall less reliably.
  • Between steps, manage the list: keep it short, clear used tool results, and compact long histories.
  • Between sessions, nothing survives unless your program saves it. Save small, exact, needed facts as notes and load them at the start.
  • For long documents, retrieve: search a store and bring only the best few pages into context, up front, just in time, or both.

Say it in your own words: without looking back, explain to a teammate why the assistant cannot simply "remember" a student from last week, and name two places the information could live instead.
